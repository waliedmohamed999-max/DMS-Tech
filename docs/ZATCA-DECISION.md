# ZATCA e-invoicing — decision gate (Phase 10)

**Status in this build: NOT IMPLEMENTED — and not faked.**

The Business OS issues VAT invoices (sequential numbers, VAT snapshot, bilingual PDF, frozen after issue). It does
**not** produce ZATCA (FATOORA) e-invoices: no UBL 2.1 XML, no cryptographic stamp, no previous-invoice hash chain,
no ZATCA QR code, no device onboarding (CSID), no clearance or reporting API. Nothing in the UI or the PDF claims
otherwise.

## Why no implementation now

Regulatory obligations depend on facts only the company and its tax advisor can confirm (VAT registration, the
company's integration wave and deadline, B2B / B2C mix, whether an existing accounting / e-invoicing system already
issues the legal tax invoice). Implementing Phase 2 integration requires the official ZATCA technical specification
and a sandbox onboarding — guessing would create invoices that look compliant and are not.

## The gate

`ZATCA_STATUS` (environment, set by the company — not inferred by the software):

| Status | Meaning | Production invoice issuing |
|---|---|---|
| `NOT_CONFIGURED` (default) | no decision recorded | **blocked** (`ZATCA_NOT_READY`) |
| `NOT_REQUIRED` + `ZATCA_DECISION_REF` | documented decision that this system's invoices are not the legal e-invoice (e.g. the legal tax invoice is issued by a compliant external system, or the advisor confirms no obligation yet) | allowed |
| `REQUIRED_NOT_READY` | the company must e-invoice and no compliant implementation exists | **blocked** |
| `READY` | only when a real `TaxInvoiceComplianceAdapter` is installed — setting the variable alone resolves to `REQUIRED_NOT_READY` | allowed |

`npm run go-live:check` BLOCKs unless the status is `NOT_REQUIRED` (with a decision reference) or `READY`.
Development, test and staging are not gated (test data only).

## Decision checklist (for management + tax advisor)

1. Is DMS Tech VAT-registered, and which ZATCA integration wave / deadline applies to it?
2. Will invoices generated by this system be sent to customers as the **legal tax invoice**?
3. Is there already a compliant e-invoicing solution (ERP / accounting software / provider) that will issue the legal invoice?
4. If this system must issue compliant invoices: obtain the current ZATCA technical spec, sandbox credentials, and plan
   an adapter project (XML, signing, QR, CSID onboarding, clearance / reporting, failure handling, archiving).

Record the answer as `ZATCA_STATUS` + `ZATCA_DECISION_REF` (minute / letter reference and approver). Until then the
invoice module may be used in staging only.

## Architecture boundary

`src/server/finance/zatca.ts` — `TaxInvoiceComplianceAdapter { prepare(invoiceId), submit(invoiceId) }`,
`complianceStatus()`, `assertInvoiceIssuingAllowed()` (called by `issueInvoice`). A future adapter registers itself
with `registerComplianceAdapter()`; only then can the status be `READY`.
